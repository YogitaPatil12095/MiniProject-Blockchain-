### One-line mental model
**A owns how it looks. B owns how it works.** The line between them is the props of a UI component.

## 3. Frontend split — the key idea

To avoid both of you editing the same React files, the frontend is split into two layers.

```
frontend/src/
├── components/ui/   ← A: dumb, pretty, props-in / events-out. No ethers, no contract calls.
├── styles/          ← A
├── mocks/           ← A
├── preview/         ← A: renders every screen with mock data
├── pages/           ← B: smart containers. Use hooks and lib, render A's components.
├── lib/ context/ hooks/  ← B
```

**A's components never import** `ethers`, `contract.json`, `lib/`, `context/` or `hooks/`.
**B's pages never contain** raw CSS or restyle A's components. They pass props and use the existing classes.

## 4. The component contract (the handoff interface)

A builds each UI component against a **props contract** written in `DESIGN.md` (or a comment at the top of the file). B wires real data into the same props. Nobody needs to touch the other's files.

Example (A writes this; B consumes it):

```jsx
// components/ui/RecordCard.jsx
// props: { creatorName: string, createdAt: number (unix seconds), cid: string, gatewayUrl: string }
// no side effects, no wallet or contract access
```

```jsx
// components/ui/StatusToast.jsx
// props: { state: 'pending' | 'success' | 'error', message: string, txHash?: string }
```

**Standard prop shapes (fixed, so both sides can work in parallel):**

| Data | Shape |
|---|---|
| Record | `{ creatorName, creatorAddress, cid, createdAt }` (`createdAt` = number, unix seconds) |
| User | `{ address, fullName, gender, homeAddress, phone, birthday }` |
| Access list | `{ viewers: string[], creators: string[] }` |
| Tx state | `{ status: 'idle'\|'pending'\|'success'\|'error', txHash?: string, message?: string }` |
| Role | `'viewer' \| 'creator' \| 'master'` |

Changing a prop shape needs both people's agreement (section 5, "Interface change").

### How A works without a blockchain
A builds and tests screens using `frontend/src/mocks/` and the pages in `frontend/src/preview/`. Run the preview at `/preview` (a route B adds once, then never touches). A never needs MetaMask, Hardhat, Pinata or `.env`.

### How B works without finished designs
B builds pages using A's existing components or temporary plain HTML with a `TODO(design)` comment. When A's component lands, B swaps it in. B does not restyle.

## 5. Change requests and conflicts

| Situation | What to do |
|---|---|
| **A needs something in B's files** (e.g., a new dependency, a route, a wrapper) | Open an issue or message: "B, please add X because Y." B does it. |
| **B needs a new/changed UI piece** | Message A with: component name, props, states needed. A builds it. Meanwhile B uses a placeholder. |
| **Interface change** (prop shape, component name, route) | Agree in chat first, then update the table in section 4 in a PR. Merge A's and B's sides within the same day. |
| **Bug in the other's area** | Report it with steps or a screenshot. Do not fix it yourself. |
| **Emergency fix in the other's file** (deadline, owner unavailable) | Allowed only with the owner's written OK (chat message). Make a tiny commit with the prefix `hotfix(A→B):` and tell the owner. |
| **Disagreement** | Owner of the area decides. If it spans both, decide together before coding. |

## 6. Git workflow

- `main` is always runnable. **No direct pushes to `main`.**
- Branches: A uses `design/<topic>`, B uses `build/<topic>`. Short-lived, merged via pull request.
- **Each PR touches only one owner's paths.** If a PR contains files from both areas, split it.
- The **other person reviews** every PR (A reviews B's and B reviews A's) using the relevant part of `REVIEW.md`. Skim; you don't need to be an expert in the other's domain.
- Commit messages: `design: …` (A), `build: …` (B), `docs: …` (either, on own docs).
- `git pull --rebase origin main` before starting each session and before opening a PR.
- Never commit `.env`, keys, or JWTs. `.gitignore` is owned by B.
- Do not reformat files you don't own (no repo-wide "format all").

### Merge-conflict avoidance
Because ownership paths don't overlap, conflicts should only appear in shared files. For `REVIEW.md`, add new entries at the bottom log, never rewrite existing lines.

## 7. Rules for AI agents (Antigravity, Stitch-to-code, etc.)

Each of you runs your own agent. **Give the agent its scope in the first prompt** and check the diff before committing.

### Agent prompt for Member A (paste at the start of the session)
```
You are helping the UI designer of this project. Read ROLES.md, DESIGN.md and AGENTS.md.
You may ONLY create or edit: design/, DESIGN.md, frontend/src/styles/, frontend/src/components/ui/,
frontend/src/mocks/, frontend/src/preview/, frontend/public/.
You must NOT edit contracts/, test/, scripts/, frontend/src/lib|context|hooks|pages/, package.json,
vite config, .env files, or contract.json. Components must be presentational: props in, events out,
no ethers, no contract or wallet access, no network calls. Use the prop shapes in ROLES.md section 4.
If something outside your scope is needed, stop and tell me what to ask the builder.
```

### Agent prompt for Member B
```
You are helping the builder of this project. Read ROLES.md, AGENTS.md, PRD.md, MEMORY.md and MILESTONES.md.
You may ONLY edit: contracts/, test/, scripts/, hardhat config, root and frontend package.json/config/.env*,
frontend/src/lib|context|hooks|pages/, README.md, PRD.md, MEMORY.md, MILESTONES.md, AGENTS.md.
You must NOT edit design/, DESIGN.md, frontend/src/styles/, frontend/src/components/ui/, frontend/src/mocks/,
frontend/src/preview/, or frontend/public/. Use the designer's components via their props; if one is missing,
use a plain placeholder marked TODO(design) and tell me what to request from the designer.
```

### Agent safety net
Before committing, run:
```bash
git status --short
```
and check every changed path against section 2. Anything outside your ownership → `git restore <path>` (or `git checkout -- <path>`) and ask the owner.

## 9. Definition of "not mixing workspaces"

You're following this file if:
- [ ] Every commit you made only touches paths you own (or shared docs)
